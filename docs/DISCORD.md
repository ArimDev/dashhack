# Discord setup

DashHack receives signed HTTP interactions in the existing Bun process. No Gateway connection, message scraper, bot daemon or extra package is needed. One Discord application/server is bound to one event; each configured team channel maps to one team.

## Organizer setup

1. Create **DashHack** at https://discord.com/developers/applications. General Information contains **Application ID** and **Public Key**.
2. In Discord enable Settings → Advanced → Developer Mode. Right-click the server and each team channel to copy their IDs. Keep team channels restricted to the appropriate students/organizers; channel access determines which team's commands they can use.
3. Log into the event in DashHack, open Settings → Discord, enter the app/key/server IDs and expand **Kanály týmů** to map channel IDs. Save. Commands may remain disabled during setup.
4. In General Information set **Terms of Service URL** to `https://dashhack-production.up.railway.app/terms.html` and **Privacy Policy URL** to `https://dashhack-production.up.railway.app/privacy.html`. These public static pages describe this private event deployment, intended mentor/organizer/student use, actual public reading, data handling and organizer contact/removal. The same URLs are shown in DashHack Settings. Set the app's **Interactions Endpoint URL** in Discord Developer Portal to `https://dashhack-production.up.railway.app/api/discord/interactions`. DashHack verifies Discord's signed PING even while commands are disabled. Do not enable privileged message/member intents or Administrator permissions.
5. Click **Nainstalovat příkazy do serveru** in DashHack and select the server. The install link requests only `applications.commands` with Guild Install context. If Discord's Installation settings restrict contexts, enable Guild Install. No mentor role is required.
6. In the application's **Bot** tab obtain/reset the bot token. Paste it only into the password field in authenticated DashHack Settings, then click **Registrovat příkazy**. The token goes over HTTPS to Discord for four guild-command upserts, is never stored/logged, and is cleared from the field after the attempt. Do not put it in chat or Git. Existing unrelated commands are retained. Rotating the token afterward does not stop signed HTTP interactions; use the new token for later command registration.
7. Enable **Povolit příkazy a formuláře**, save, and test `/mentor`, `/matice` and `/github` in a mapped team channel. Discord may take a short time to expose guild commands. Unknown channels/servers and bot senders are rejected privately.

## Commands

- `/mentor` opens a short text modal. Submission creates a team-colored `help_request`, tracked in Kanban, To Do, medium priority. The modal includes **Naléhavost**: **Běžná** (medium, default) or **Naléhavá** (high). The slash command needs no arguments. Older already-open modals remain compatible. Students cannot set Critical or attribute themselves as an event mentor. Verified Discord display name is appended; the numeric Discord user ID is stored in the event's private audit.
- `/matice` responds only to the requesting user with a link to their team's ten rich-text answers. The page supports partial answers, bold/italic/bullets, revision-checked saves and retained conflict drafts. Existing mentor attribution and other team data remain intact. Students do not receive the event password or an organizer session. The existing organizer XLSX exports include these saved answers.

- `/github` privately returns the mapped team's existing organizer-issued GitHub joining link, using the same `/join#TOKEN` OAuth account verification as the organizer links. It never asks for a typed GitHub username or grants access directly. Each delivery revalidates event/team scope, expiry, revocation, repository and installation. It does not create or replace invitation links; organizers prepare/refresh those in GitHub App settings. The recreated test team's link is prepared separately through the organizer API. Delivery is audited by verified Discord account ID, with no raw bearer URL stored in the audit; limits are 10/user and 20/team per ten minutes. Repeated Discord delivery reuses the result without consuming another allowance, but still rechecks revocation.

The same channel maps all teammates to the same team. This does not verify roster membership beyond access to that Discord channel. Organizers must configure channel permissions; a student who can run commands in another team's configured channel can submit for that team.

## Security and limits

- Verify Ed25519 over the exact timestamp/raw body before handling PING or commands; reject timestamps more than five minutes away. The interaction body is bounded at 256 KiB with a ten-second read deadline. Invalid signatures use HTTP 401.
- Duplicate interaction IDs return the original result without creating another note or spending another submission allowance. Mentions are disabled in replies. No interaction payloads/tokens or bot token are logged/persisted.
- Matrix links carry a random flow ID plus HMAC in the URL fragment. The page removes it from browser history before fetching. A link must be claimed within ten minutes, once per browser; a separate HttpOnly/Secure/SameSite=Strict cookie grants only that team's matrix access until two hours after issuance. Links are bearer capabilities until claimed: forwarding an unused link permits the recipient to claim it. They are ephemeral Discord replies, not public team URLs.
- Every matrix read/write rechecks flow expiry, enabled settings, team existence and channel mapping. Saving settings rotates the link key and deletes all outstanding flows, including active student sessions. Disabling commands therefore stops existing forms too. Students can reopen `/matice` after setup changes.
- Rate windows are ten minutes: help submissions **5/user, 10/team**; form links **10/user, 20/team**; matrix saves **30/user, 100/team**. Discord delivery retries do not count again. The event is capped at 5,000 audit actions and 500 live form flows, with 1,000 notes per team. Expired flows and audit rows older than seven days are pruned when handling new actions. Latest 50 actions are visible to event organizers in Settings. These limits are SQLite-enforced and survive restarts; no IP identity is used.
- Form saves require the scoped cookie before buffering up to 6 MiB of rich-text JSON, enforce same origin, and reuse the matrix's ten keys/600-character per-answer limits and printable line budget. No names or answers are rendered as raw HTML. Stale team revisions reject the entire patch and retain the browser draft.
- Private configuration/audit endpoints require the ordinary matching event session. The public event API/export does not expose settings, flow secrets or Discord audit tables. Existing public read behavior is unchanged.

Schema 9 adds `discord_settings`, `discord_actions` and `discord_matrix_flows` transactionally without changing existing content. Full private SQLite backups include these records; public event JSON does not. Back up on the volume before deployment. One web replica remains required.

## Mentor-channel announcements

New tracked `help_request` notes from `/mentor` and DashHack are queued transactionally in SQLite. Ordinary mentor notes and edits do not announce again. Historical requests are not enqueued by migration. One message per note shows a team-colored embed (amber/red for urgent/critical), team, priority, author, problem excerpt and an **Otevřít v Kanbanu** link. The `?note=ID` link highlights the card, scrolls it into view and selects its actual column on phones. It does not grant editing access.

Set private runtime variable `NUXT_DISCORD_BOT_TOKEN` on DashHack in Railway. The registration form never retains its token; ongoing message delivery needs this server-side configuration. `NUXT_DISCORD_MENTOR_CHANNEL_ID` identifies the one target channel (this event: `1285378043099086852`). The app base URL uses the configured GitHub App base URL, or Railway's public domain if absent. Do not commit or send the token in chat.

Install the same application with `bot applications.commands` scopes and minimal permissions **View Channel, Send Messages, Embed Links** (19456). Permit these in mentor-chat's channel overrides. The setup panel includes this install link and token/configuration/delivery status. No Gateway connection, privileged intents or message-history reads are needed. The bot can appear offline because delivery uses REST only. No slash-command re-registration is needed for notifications if the four existing definitions are already installed.

Before sending, the server verifies the token's application ID and target channel's guild against the event's Discord settings. Wrong app/guild cannot receive notes. User-supplied mentions are disabled and user Markdown escaped; excerpts are bounded. Optional `NUXT_DISCORD_MENTOR_ROLE_ID` pings only one verified mentionable role in the target guild using an explicit allowed-mentions whitelist. This event uses Mentor `1285378042478329872`; no @everyone permission is needed. Full bot credentials never enter SQLite, API responses, public exports, URLs or logs.

Schema 10 adds `discord_notifications`: a bounded per-note delivery marker/queue (5,000 rows/event, seven-day cleanup when the worker runs). It deliberately has no note foreign key because existing whole-team saves replace note rows. Markers survive those saves; deleting a team/event clears them. A removed/untracked request is skipped before posting. A small in-process worker wakes every 15 seconds only with token/channel configured, and new saves can trigger it immediately without waiting for network delivery in the HTTP response; empty queues cause no Discord API requests. There is no separate service, SDK or paid social-provider polling. Disabling Discord on the event pauses queued announcements too.

A request always remains in Kanban if Discord delivery fails. A persisted send claim plus stable Discord nonce prevents retry duplicates. Only explicit rate-limit rejections are retried (respecting delay, at most three attempts); credential/channel verification failures also stop after three checks. Ambiguous network/5xx results and interrupted sends are recorded as failed and are not automatically resent, favoring no duplicate alerts over guaranteed delivery. Organizer Settings shows counts and safe failure text; existing failed messages require organizer review, not an endless retry loop. Posted cards now synchronize as described below; deleting a team/event still requires manual cleanup of its Discord copies. Privacy/Terms describe this additional sharing.

## Completing and reopening requests (schema 11)

Kanban cards have **Complete**, **To Do**, and **In Progress** actions for the other columns. Discord mentor cards have **K vyřízení**, **Řeší se**, and **Hotovo** buttons; the current status is disabled. Done is reversible. Existing sent cards receive these controls on upgrade, with no new message or role ping. No slash command re-registration or extra bot permissions are needed.

Discord status actions require a valid signed interaction, the configured application/guild, exact mentor channel, the stored message/note binding and membership in `NUXT_DISCORD_MENTOR_ROLE_ID`. This does not grant an event login or access to another team's data. The existing Discord action audit records the verified mentor account and previous/new status. Interaction retries are idempotent; stale buttons are rejected rather than overwriting a newer status. The transaction updates only note status, increments the team's revision and preserves all other fields.

Schema 11 adds delivery channel, message fingerprint and bounded edit-retry fields. The in-process worker streams stored cards and PATCHes at most five changed cards per tick, only when their rendered contents differ. Successful status/content/priority edits update the same message with mentions explicitly disabled and the original ping removed. No idle Discord API calls occur. Safe PATCH retries back off and stop after three attempts per rendered version; 403/404 stop immediately. An in-flight older edit cannot mark a newer version synchronized. Deleted/untracked notes show Neaktivní and disabled buttons; deleting a team/event removes the tracking row, so organizers must remove its Discord copy separately. Sync tracking retains the existing seven-day window. Disabling the event's Discord integration pauses sync too.

The visible Kanban refreshes every 15 seconds while idle, preserving active form editing; a hidden browser tab does not poll. Changes from Discord therefore appear without manually reloading. Direct app saves also kick the worker; the 15-second fallback handles work already in progress or interrupted delivery. Network failures leave the authoritative Kanban note intact and a safe error in event settings.

## Done tickets thread (schema 12)

The existing bot already has Create Public Threads and Send Messages in Threads, so no reinstall was needed. The thread inherits visibility from mentor-chat. No privileged intents, SDK, worker service or Administrator permission.

Done cards have a green checkmarked header, a compact excerpt and **Znovu otevřít**. A Mentor-role click reopens the same Kanban note; Kanban reopening works too. Discord cannot change a message's channel, so a move creates a replacement bot card, persists its receipt/current binding and a cleanup job in one SQLite transaction, then deletes the previous bot card. Returning to mentor-chat creates a new message at the bottom of its feed. Replacements have no role/user pings. Old Discord message URLs change, and human replies/attachments/reactions are not moved; the authoritative Kanban deep link and note ID stay the same. The full note text stays in DashHack.

Schema 12 adds `discord_notifications.move_state` and bounded `discord_message_cleanup` rows. The pre-I/O claim and deterministic enforced nonce prevent automatic duplicate copies; ambiguous timeouts/5xx/invalid receipts or interrupted copies stop for organizer review, retain the old card and never automatically retry the POST. Only explicit rejected 429s retry with backoff, at most three times per rendered version. Confirmed old-card DELETE retries are safe and bounded at three; 404 counts as cleaned. Failed cleanup leaves a stale card, whose buttons are rejected by the exact current-message binding; event Settings shows the safe error. Do not reset an uncertain move without checking Discord for an already-created replacement. Migration itself never sends or deletes messages. The existing 15-second in-process tick handles transfers and cleanup; idle cards cause no provider calls.

Disabled integration pauses copying and cleanup. With no Done-thread ID, green completed cards stay in mentor-chat. Archiving the unlocked thread is handled by Discord when a new card is posted (posting unarchives it); leave it unlocked. Deleting a team/event removes delivery/cleanup tracking, so organizers still handle any remaining Discord copies manually. No new slash command registration is necessary.

## Matrix answer visibility follow-up

Team matrices share one stored answer set between the student Discord form and mentor dashboard. The dashboard previously held its route-load snapshot until navigation, so externally saved answers could remain invisible in an already-open Teams tab. Teams now reads a fresh event snapshot when a matrix opens, on window focus, via Refresh and every 15 seconds while a matrix is open in a visible tab. Refresh is blocked during any matrix draft (including collapsed drafts), modal, focused form control or queued note save. The response is discarded if the event, state object or team revisions changed during its read, preserving newer edits and normal conflict checks. No extra service, dependency, schema or API endpoint.
